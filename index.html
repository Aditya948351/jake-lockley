Executive summary

PM‑AJAY is an offline‑first Android app (Jetpack Compose) with officer/admin web portals. It enables document capture, on-device ML verification, secure uploads to Cloudinary, authoritative storage and sync in Firebase, a CP (Community Points) engine, and PFMS integration for payouts.
Core goals:
  • Faster, auditable benefit delivery for low‑connectivity, low‑literacy citizens.
  • Privacy-preserving on‑device verification (OCR, face match, liveness).
  • Learn‑and‑earn CP engine that circulates value locally via merchant redemption.
  • Officer + Admin workflows to verify, approve and reconcile funds (PFMS).

Why we are building this — Government hardships

  • Low accessibility & digital literacy: Many beneficiaries cannot use web portals; offline & local language support is essential.
  • High verification cost & delays: Repeated field travel and manual paperwork slows disbursement.
  • Data fragmentation & leakage: Paper systems cause duplicates, ghost claims, and poor audit trails.
  • Poor impact measurement: Slow reporting hinders policy response — we provide near‑real‑time KPIs.
  • Local economic under‑circulation: CPs redeemed at local merchants stimulate local economies, creating multiplier effects.

On‑device ML & Hosted fallback

On‑device (preferred)

  • OCR: ML Kit Text Recognition or TFLite OCR for extracting name, DOB, ID fragments (mask Aadhaar except last4).
  • Face detection & embeddings: MobileFaceNet / TFLite embedding model + cosine similarity for selfie ↔ ID photo comparison (thresholds: >=0.75 accept, 0.6–0.75 manual review).
  • Liveness: Blink/head-turn via MediaPipe landmarks or small TFLite liveness model.
  • Document QC: Blur/glare/rotation checks to require retake prior to upload.

Hosted fallback (optional)

Use Hugging Face / Render endpoints for high‑accuracy OCR, face‑match or batch reprocessing of ambiguous items. Keep calls server-side and cache results.

Community Points (CP) engine & Leaderboard

  • Rules: cp_rules table drives events → points mapping, daily/month caps enforced at DB level.
  • Award flow: POST CP event (idempotent) → insert cp_transaction → atomically update cp_balance (SELECT FOR UPDATE) → write audit → push leaderboard update to Firebase (Realtime DB / Firestore).
  • Leaderboard: Stored in Firebase for realtime reads; backend is source-of-truth (DB) and writes leaderboard increments after DB commit (retry on failure).
  • Streaks: /streak/claim locks user row and enforces 24‑hour window; award CP if allowed.

Security, privacy & compliance

  • Aadhaar & PII: never store raw Aadhaar; store HMAC‑SHA256(aadhaar + salt) + last4; capture explicit consent; run legal review before any UIDAI eKYC integration.
  • Auth & RLS: Firebase Auth for identity; backend maps auth_uid → users and enforces server-side checks; Firestore security rules + backend RLS-like checks for domain logic.
  • Encryption: TLS everywhere; Cloudinary + Firebase encrypted at rest; local device storage encryption via AndroidKeyStore & EncryptedFile.
  • Audit: append-only audit_logs for all mutating actions (actor, role, action, old/new payload masked).
  • Secrets: store service keys in secret vault/CI secrets; rotate regularly.
